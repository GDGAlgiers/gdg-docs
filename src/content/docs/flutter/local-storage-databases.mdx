Effective local data storage is crucial for creating responsive, offline-capable Flutter applications. Understanding the different storage solutions and when to use each will help you build more reliable and performant apps.

<Aside type="tip">
  **Pro tip:** Plan your data persistence strategy early in development. Changing storage approaches later can be costly and time-consuming.
</Aside>

## Choosing the Right Storage Solution

Flutter offers several storage options, each optimized for different use cases. Select the right tool based on your data complexity and requirements.

### Quick Decision Guide

**Simple key-value data** → SharedPreferences  
**Structured objects without relations** → Hive  
**Relational data with type safety** → Drift (SQLite)  
**Direct SQL control** → SQFlite

### Storage Options Overview

<Tabs>
  <TabItem label="SharedPreferences">
    **Simple Key-Value Storage**
    
    - **Best for**: User settings, preferences, simple flags
    - **Data types**: Primitives (String, int, bool, double) and String lists
    - **Use case**: Small amounts of non-structured data
    
    **When to use**: Storing user preferences, app configuration, and simple application state.
  </TabItem>
  
  <TabItem label="Hive">
    **Fast NoSQL Database**
    
    - **Best for**: Moderate-sized structured data
    - **Data types**: Dart objects with type adapters
    - **Use case**: Storing objects without complex relationships
    
    **When to use**: Fast read/write operations with structured data that doesn't require SQL queries.
  </TabItem>
  
  <TabItem label="Drift">
    **Type-Safe SQLite Wrapper**
    
    - **Best for**: Complex relational data
    - **Data types**: SQL tables with Dart type safety
    - **Use case**: Data with relationships and complex queries
    
    **When to use**: Applications requiring relational data, compile-time safety, and reactive streams.
  </TabItem>
  
  <TabItem label="SQFlite">
    **Direct SQLite Access**
    
    - **Best for**: Raw SQL control
    - **Data types**: SQL data types
    - **Use case**: Complex queries and SQL optimization
    
    **When to use**: Maximum control over SQL, migrating existing SQLite databases, or custom query optimization.
  </TabItem>
</Tabs>

## SharedPreferences

SharedPreferences provides simple key-value storage for primitive data types. It's the simplest storage solution and perfect for user settings and preferences.

### Basic Usage

**Add the dependency:**

<Code code={`dependencies:
  shared_preferences: ^2.2.0`} lang="yaml" />

**Store and retrieve data:**

<Code code={`// Store different data types
Future<void> saveUserPreferences() async {
  final prefs = await SharedPreferences.getInstance();
  
  // Store basic types
  await prefs.setString('username', 'flutter_user');
  await prefs.setBool('darkMode', true);
  await prefs.setInt('launchCount', 10);
  await prefs.setStringList('recentSearches', ['flutter', 'dart']);
}

// Retrieve values with defaults
Future<void> loadUserPreferences() async {
  final prefs = await SharedPreferences.getInstance();
  
  // Get values with fallback defaults
  final username = prefs.getString('username') ?? 'Guest';
  final isDarkMode = prefs.getBool('darkMode') ?? false;
  final launchCount = prefs.getInt('launchCount') ?? 0;
  
  // Increment launch count
  await prefs.setInt('launchCount', launchCount + 1);
}`} lang="dart" title="Basic Operations" />

### Organizing with Constants

Use constants for keys to avoid typos and improve maintainability:

<Code code={`// Define preference keys as constants
class PreferenceKeys {
  static const String username = 'username';
  static const String darkMode = 'darkMode';
  static const String launchCount = 'launchCount';
}

// Usage with constants
await prefs.setBool(PreferenceKeys.darkMode, true);`} lang="dart" />

### Creating a Preferences Service

Encapsulate SharedPreferences logic in a service class for better organization:

<Code code={`// Preferences service for better code organization
class PreferencesService {
  late SharedPreferences _prefs;
  
  // Initialize the service
  Future<void> init() async {
    _prefs = await SharedPreferences.getInstance();
  }
  
  // Getters with default values
  String get username => _prefs.getString(PreferenceKeys.username) ?? 'Guest';
  bool get isDarkMode => _prefs.getBool(PreferenceKeys.darkMode) ?? false;
  
  // Setters return Future for async operations
  Future<void> setUsername(String value) => 
      _prefs.setString(PreferenceKeys.username, value);
  
  Future<void> setDarkMode(bool value) => 
      _prefs.setBool(PreferenceKeys.darkMode, value);
}`} lang="dart" title="Preferences Service" />

<Aside type="caution">
  **Limitations**: SharedPreferences only supports primitive types (bool, int, double, String) and String lists. Not suitable for structured data, large datasets, or high-frequency operations.
</Aside>

## Hive

Hive is a lightweight, blazing-fast NoSQL database written in pure Dart. It's perfect for storing structured data without the complexity of SQL.

**Add dependencies:**

<Code code={`dependencies:
  hive: ^2.2.3
  hive_flutter: ^1.1.0

dev_dependencies:
  hive_generator: ^2.0.1
  build_runner: ^2.4.6`} lang="yaml" />

### Defining Models

Create type-safe models with Hive's code generation:

<Code code={`import 'package:hive/hive.dart';

// Generate adapter with: flutter pub run build_runner build
part 'task.g.dart';

@HiveType(typeId: 0)  // Unique ID for each model (0-223)
class Task extends HiveObject {
  @HiveField(0)
  final String id;
  
  @HiveField(1)
  String title;
  
  @HiveField(2) 
  bool completed;
  
  Task({
    required this.id,
    required this.title,
    this.completed = false,
  });
}`} lang="dart" title="Model Definition" />

**Generate the adapter:**

<Code code={`# Run code generation
flutter pub run build_runner build`} lang="bash" />

### Basic Operations

Initialize Hive and perform CRUD operations:

<Code code={`// Initialize Hive in your app
import 'package:hive_flutter/hive_flutter.dart';

void main() async {
  // Initialize Hive
  await Hive.initFlutter();
  
  // Register adapters
  Hive.registerAdapter(TaskAdapter());
  
  // Open boxes
  await Hive.openBox<Task>('tasks');
  
  runApp(MyApp());
}

// CRUD operations
class TaskRepository {
  late Box<Task> _taskBox;
  
  Future<void> init() async {
    _taskBox = Hive.box<Task>('tasks');
  }
  
  // Create or Update
  Future<void> saveTask(Task task) async {
    await _taskBox.put(task.id, task);
  }
  
  // Read
  Task? getTask(String id) {
    return _taskBox.get(id);
  }
  
  // Get all tasks
  List<Task> getAllTasks() {
    return _taskBox.values.toList();
  }
  
  // Delete
  Future<void> deleteTask(String id) async {
    await _taskBox.delete(id);
  }
}`} lang="dart" title="Hive Operations" />

<Aside type="tip">
  **Performance tip**: Use unique typeIds (0-223) for each model. Close boxes when no longer needed to free up resources.
</Aside>

## Drift (SQLite)

Drift is a reactive persistence library that builds on SQLite, providing type safety and code generation for complex relational data.

**Add dependencies:**

<Code code={`dependencies:
  drift: ^2.14.0
  sqlite3_flutter_libs: ^0.5.0
  path_provider: ^2.1.0
  path: ^1.8.0

dev_dependencies:
  drift_dev: ^2.14.0
  build_runner: ^2.4.0`} lang="yaml" />

### Table Definition

Define your database schema with Drift's table classes:

<Code code={`import 'package:drift/drift.dart';

// Define table structure
class Tasks extends Table {
  IntColumn get id => integer().autoIncrement()();
  TextColumn get title => text().withLength(min: 1, max: 100)();
  BoolColumn get completed => boolean().withDefault(const Constant(false))();
  DateTimeColumn get createdAt => dateTime().withDefault(currentDateAndTime)();
}

// Generate code with: flutter pub run build_runner build
part 'database.g.dart';

@DriftDatabase(tables: [Tasks])
class AppDatabase extends _\$AppDatabase {
  AppDatabase() : super(_openConnection());
  
  @override
  int get schemaVersion => 1;
  
  // Query methods
  Future<List<Task>> getAllTasks() => select(tasks).get();
  
  // Reactive stream for real-time updates
  Stream<List<Task>> watchAllTasks() => select(tasks).watch();
  
  Future<int> addTask(TasksCompanion task) => 
      into(tasks).insert(task);
  
  Future<bool> updateTask(TasksCompanion task) => 
      update(tasks).replace(task);
  
  Future<int> deleteTask(int id) => 
      (delete(tasks)..where((t) => t.id.equals(id))).go();
}

// Database connection setup
LazyDatabase _openConnection() {
  return LazyDatabase(() async {
    final dbFolder = await getApplicationDocumentsDirectory();
    final file = File(join(dbFolder.path, 'app.db'));
    return NativeDatabase(file);
  });
}`} lang="dart" title="Database Setup" />

### Reactive UI Updates

Drift's reactive streams automatically update your UI when data changes:

<Code code={`// UI automatically updates when data changes
StreamBuilder<List<Task>>(
  stream: database.watchAllTasks(),
  builder: (context, snapshot) {
    if (snapshot.connectionState == ConnectionState.waiting) {
      return const CircularProgressIndicator();
    }
    
    final tasks = snapshot.data ?? [];
    
    return ListView.builder(
      itemCount: tasks.length,
      itemBuilder: (context, index) {
        final task = tasks[index];
        return ListTile(
          title: Text(task.title),
          leading: Checkbox(
            value: task.completed,
            onChanged: (value) {
              // Update triggers automatic UI refresh
              database.updateTask(
                task.copyWith(completed: Value(value ?? false)),
              );
            },
          ),
        );
      },
    );
  },
)`} lang="dart" title="Reactive UI" />

<Aside type="note">
  **Type safety**: Drift provides compile-time type checking, eliminating runtime SQL errors and improving code reliability.
</Aside>

## SQFlite

SQFlite provides direct access to SQLite, giving you full control over SQL operations.

**Add dependencies:**

<Code code={`dependencies:
  sqflite: ^2.3.0
  path: ^1.8.0`} lang="yaml" />

### Database Setup

Create a database helper class using the singleton pattern:

<Code code={`import 'package:sqflite/sqflite.dart';
import 'package:path/path.dart';

// Singleton database helper
class DatabaseHelper {
  static final DatabaseHelper instance = DatabaseHelper._init();
  static Database? _database;
  
  DatabaseHelper._init();
  
  Future<Database> get database async {
    if (_database != null) return _database!;
    _database = await _initDB('app_database.db');
    return _database!;
  }
  
  Future<Database> _initDB(String filePath) async {
    final dbPath = await getDatabasesPath();
    final path = join(dbPath, filePath);
    
    return await openDatabase(
      path,
      version: 1,
      onCreate: _createDB,
    );
  }
  
  Future<void> _createDB(Database db, int version) async {
    // Create tables
    await db.execute('''
      CREATE TABLE tasks(
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        title TEXT NOT NULL,
        completed INTEGER NOT NULL DEFAULT 0,
        created_at INTEGER NOT NULL
      )
    ''');
  }
  
  // Close database
  Future<void> close() async {
    final db = await database;
    db.close();
  }
}`} lang="dart" title="Database Helper" />

### CRUD Operations

Implement basic database operations:

<Code code={`class TaskRepository {
  // Create
  Future<int> createTask(String title) async {
    final db = await DatabaseHelper.instance.database;
    return await db.insert('tasks', {
      'title': title,
      'completed': 0,
      'created_at': DateTime.now().millisecondsSinceEpoch,
    });
  }
  
  // Read all
  Future<List<Map<String, dynamic>>> getAllTasks() async {
    final db = await DatabaseHelper.instance.database;
    return await db.query('tasks', orderBy: 'created_at DESC');
  }
  
  // Read one
  Future<Map<String, dynamic>?> getTask(int id) async {
    final db = await DatabaseHelper.instance.database;
    final results = await db.query(
      'tasks',
      where: 'id = ?',
      whereArgs: [id],
    );
    return results.isNotEmpty ? results.first : null;
  }
  
  // Update
  Future<int> updateTask(int id, bool completed) async {
    final db = await DatabaseHelper.instance.database;
    return await db.update(
      'tasks',
      {'completed': completed ? 1 : 0},
      where: 'id = ?',
      whereArgs: [id],
    );
  }
  
  // Delete
  Future<int> deleteTask(int id) async {
    final db = await DatabaseHelper.instance.database;
    return await db.delete(
      'tasks',
      where: 'id = ?',
      whereArgs: [id],
    );
  }
}`} lang="dart" title="CRUD Operations" />

<Aside type="tip">
  **Drift vs SQFlite**: Drift provides compile-time type safety and eliminates SQL string errors, while SQFlite offers more direct control. Choose Drift for type safety, SQFlite for SQL flexibility.
</Aside>

## Offline Data Synchronization

Implementing effective offline capabilities ensures your app remains functional without internet connectivity.

### Synchronization Strategies

<Tabs>
  <TabItem label="Basic Sync">
    **Simple Upload/Download**: Download remote data, upload local changes. Best for simple data models with rare conflicts.
    <Code code={`class BasicSyncService {
  final ApiService _api;
  final TaskRepository _repository;
  
  BasicSyncService(this._api, this._repository);
  
  Future<void> syncTasks() async {
    try {
      // Download remote changes
      final remoteTasks = await _api.fetchTasks();
      for (var task in remoteTasks) {
        await _repository.saveTask(task);
      }
      
      // Upload local changes
      final localTasks = await _repository.getPendingUploads();
      for (var task in localTasks) {
        await _api.uploadTask(task);
        await _repository.markAsSynced(task.id);
      }
    } catch (e) {
      // Handle connectivity issues
      print('Sync failed: \$e');
    }
  }
}`} lang="dart" />
  </TabItem>

  <TabItem label="Timestamp-Based">
    **Track Changes by Time**: Use timestamps to sync only what changed. Best for collaborative apps with frequent updates.
    <Code code={`class TimestampSyncService {
  final ApiService _api;
  final TaskRepository _repository;
  
  Future<void> syncTasks() async {
    try {
      // Get last sync timestamp
      final lastSync = await _repository.getLastSyncTimestamp();
      
      // Fetch only changes since last sync
      final remoteChanges = await _api.getChangesSince(lastSync);
      for (var change in remoteChanges) {
        await _repository.applyRemoteChange(change);
      }
      
      // Upload local changes
      final localChanges = await _repository.getChangesSince(lastSync);
      for (var change in localChanges) {
        await _api.uploadChange(change);
      }
      
      // Update sync timestamp
      await _repository.setLastSyncTimestamp(DateTime.now());
    } catch (e) {
      // Handle sync errors
      print('Sync failed: \$e');
    }
  }
}`} lang="dart" />
  </TabItem>

  <TabItem label="Queue-Based">
    **Operation Queue**: Queue all operations for sequential sync. Best for mission-critical data where order matters.
    <Code code={`class QueueSyncService {
  final ApiService _api;
  final SyncQueueRepository _queueRepo;
  
  // Add operation to queue
  Future<void> addTask(Task task) async {
    await _queueRepo.addToQueue(
      SyncOperation(
        type: SyncOperationType.create,
        entityType: 'task',
        data: task.toMap(),
        timestamp: DateTime.now(),
      ),
    );
    
    // Try to process queue immediately
    processQueue();
  }
  
  // Process queued operations
  Future<void> processQueue() async {
    if (!await _hasConnectivity()) return;
    
    final operations = await _queueRepo.getOperationsToSync();
    
    for (var op in operations) {
      try {
        // Execute operation based on type
        switch (op.type) {
          case SyncOperationType.create:
            await _api.create(op.entityType, op.data);
            break;
          case SyncOperationType.update:
            await _api.update(op.entityType, op.data);
            break;
          case SyncOperationType.delete:
            await _api.delete(op.entityType, op.data['id']);
            break;
        }
        
        // Mark as synced
        await _queueRepo.markAsSynced(op.id);
      } catch (e) {
        // Keep in queue for retry if server error
        if (!_isServerError(e)) {
          await _queueRepo.markAsFailed(op.id, e.toString());
        }
      }
    }
  }
  
  Future<bool> _hasConnectivity() async {
    // Check internet connection
    return true;
  }
  
  bool _isServerError(Exception e) {
    // Determine if 5xx vs 4xx error
    return false;
  }
}`} lang="dart" />
  </TabItem>
</Tabs>

### Conflict Resolution

When the same data is modified offline and online, you need a strategy to resolve conflicts:

**Server Wins**: Always prefer server data. Simple but may lose local changes.

**Client Wins**: Local changes override server data. Preserves user edits but may overwrite others' updates.

**Last Write Wins**: Use timestamps to determine the newest change. Requires clock synchronization.

**Manual Resolution**: Let users resolve conflicts. Most user-friendly but adds complexity.

## Best Practices Summary

### Storage Best Practices

<Steps>
  1. **Choose the right tool** for each data type
  
  2. **Use repository pattern** to encapsulate storage logic
  
  3. **Handle errors gracefully** with proper try-catch blocks
  
  4. **Implement migrations** for schema changes
  
  5. **Close resources** properly to prevent memory leaks
  
  6. **Test offline scenarios** to ensure data integrity
</Steps>

### Common Mistakes to Avoid

**Storing large data in SharedPreferences**
- Use Hive or SQLite for structured or large datasets
- SharedPreferences is only for simple key-value pairs

**Blocking the UI thread**
- Always use async/await for database operations
- Never perform database calls synchronously

**Ignoring database migrations**
- Plan for schema changes from the start
- Test migrations thoroughly before deployment

**Not handling offline mode**
- Implement proper connectivity checks
- Queue operations for later sync when offline

**Missing error handling**
- Always wrap database operations in try-catch
- Provide meaningful error messages to users
